# Deux versions en parallèle

## En un coup d'œil

| | `main` — **v1** | `v2` |
|---|---|---|
| Ce que c'est | La version qui part en spectacle | Le chantier 3D |
| Dernière version | 1.6.0 (releases publiées) | rien encore, part de 1.6.0 |
| État | **Stable, à ne pas déstabiliser** | En construction |
| Ce qu'on y fait | Corrections et petites améliorations | Scénographie et effets 3D |
| Releases GitHub | oui | pas avant qu'elle soit prête |

**La règle** : `main` reste utilisable à tout moment. Tant que la v2 n'est pas
finie, c'est elle qu'on télécharge, qu'on installe et qu'on emmène en salle.

## Pour Pym, concrètement

Rien ne change pour toi tant que je ne te dis pas le contraire. Les exécutables
de la page des releases restent ceux de la v1.6. Si un bug apparaît en
spectacle, on le corrige sur `main` et on publie une 1.6.1 — le chantier 3D
n'entre pas en jeu.

Quand la v2 sera présentable, tu l'essaieras à côté de la v1 (elles peuvent
cohabiter : chacune écrit sa propre configuration à côté de son exécutable).
Elle ne remplacera la v1 que le jour où tu l'auras validée sur ta scéno.

## Pour celui qui code

- Un correctif qui concerne les deux : le faire sur `main`, puis
  `git checkout v2 && git merge main`. Jamais l'inverse.
- Une nouveauté v2 : uniquement sur `v2`.
- `npm test` doit passer sur les deux branches, tout le temps.
- `node sync-dist.js` avant de conclure, sur les deux branches
  (un test échoue si `dist/` diverge).
- Le plan du chantier : [`PLAN-V2.md`](PLAN-V2.md). Sa section 7 liste les
  vérifications à faire **avec MadMapper ouvert avant d'écrire du code** —
  trois d'entre elles peuvent changer le plan.

## Quand v2 remplacera v1

Le jour où la v2 est validée sur une vraie scéno :

```bash
git checkout main && git merge v2   # v2 devient la version courante
```

et la v1 reste consultable par son tag `v1.6.0`.
